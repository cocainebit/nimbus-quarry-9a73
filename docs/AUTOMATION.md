# Generated-app workflows, jobs and files

Owners build workflows in **App backend → Workflow builder**. Choose a collection, record event (created/updated/deleted) or schedule, optional field conditions, and up to ten ordered actions. Actions are literal member notifications, HTTPS webhooks, or an update to one field on the triggering record. The editor supports editing/reordering steps, enabling/disabling workflows, execution progress and retrying remaining steps.

Conditions use AND semantics: equals, notEquals, numeric greaterThan/lessThan, text contains or exists. Conditions inspect the triggering snapshot before enqueueing. Unknown fields and invalid update values are rejected on save. Record updates recheck current membership, ownership/editor permission, field types, uniqueness, references, immutable fields and allowed transitions under the same project lock as interactive writes. Record-update actions deliberately do not emit new workflow events, preventing recursive loops. Conditions are not re-evaluated between steps, and multiple steps are independently committed, not one all-or-nothing transaction.

One-time and minute-interval schedules persist their next execution in PostgreSQL. Concurrent schedulers lock due workflows and enqueue a unique workflow/time-slot key in the same transaction that advances the next run. Restarting the process preserves schedules. After downtime, recurring schedules enqueue one due tick and skip the missed ticks while preserving cadence. Times are stored as UTC instants; the editor accepts local time. Calendar cron, timezone/DST calendars and bulk scheduled record mutation are not implemented. Schedule notifications require an explicit member of that app as recipient; they never implicitly target the builder account. Archived projects pause new schedule enqueues and job claims; restoring them resumes processing. A step already executing may finish. Disabling/deleting workflows prevents new enqueues; queued jobs retain their original definitions.

Each job snapshots its ordered steps. Database effects and a `job_steps` completion marker commit atomically. A later failure or crash retries only unfinished steps. Workers hold the job row lock while executing each step and use crash-recovery leases, exponential retry backoff and a five-attempt limit. Notification uniqueness is scoped to job and step. Legacy API callers may still provide one `action` instead of `actions`.

Webhook delivery remains **at least once**: a crash after the receiver accepts but before the database commits can resend. Receivers must deduplicate the stable `Idempotency-Key` (`jobId:stepIndex`). Earlier successfully committed steps are never repeated on manual retry. Jobs and step history are retained until project deletion; pruning and arbitrary script execution are not implemented.

## Queue design research

PostgreSQL explicitly documents SKIP LOCKED as useful for consumers of a queue-like table ([PostgreSQL SELECT reference](https://www.postgresql.org/docs/current/sql-select.html)). [pg-boss](https://github.com/timgit/pg-boss) packages PostgreSQL queues, retries and scheduling. We retained the existing database queue rather than introducing a second queue lifecycle and migration system: record changes and event enqueue already share a transaction, and the current scope is bounded declarative actions. This is an implementation tradeoff, not a claim to pg-boss or Temporal feature parity. A distributed runtime, complex DAGs or high-volume scheduling warrants reevaluation.

## Webhook configuration

The server operator explicitly sets `WEBHOOK_ALLOWED_HOSTS=api.example.com,hooks.example.org`. Only exact HTTPS hostnames on port 443 are permitted; credentials in URLs and fragments are rejected. Configure optional bearer tokens in server environment variables such as `WEBHOOK_SECRET_CRM_TOKEN`; also bind each secret to its exact destination URL with `WEBHOOK_SECRET_URL_CRM_TOKEN=https://api.example.com/hook` and its project ID with `WEBHOOK_SECRET_PROJECT_CRM_TOKEN=<project-id>`. Owners enter the reference `CRM_TOKEN`, never the secret itself. Missing or mismatched bindings reject delivery. Avoid including secrets in webhook URLs.

At execution time the worker resolves DNS, rejects private/reserved IPv4 addresses and all IPv6 addresses, pins the validated address to the HTTPS connection while retaining TLS hostname verification, rejects redirects and applies a request deadline. DNS and host policies are rechecked for retries. Providers requiring IPv6-only endpoints are unsupported. Configure only receivers authorized to receive app records; webhook payloads include the triggering record and actor identifier. Error/status APIs never expose bearer secrets. Automated tests inject a fake transport and send no real webhook messages.

## Private files

Published app members can upload `POST /api/apps/:slug/files` with JSON `{ "name": "notes.txt", "mime": "text/plain", "base64": "..." }`. Supported types: PNG, JPEG, WebP, PDF, plain text and CSV. Content has basic signature checks, a 5 MB per-file limit, a 100 MB per-app limit and a 1,000-file per-app limit. Storage is PostgreSQL `bytea`, so files are covered by the same database backup.

List a member's files with `GET /api/apps/:slug/files`; authenticated downloads and deletion use `/api/apps/:slug/files/:fileId`. A file is private to its uploader and its app. Downloads are attachments with `nosniff`, a restrictive CSP and no-store caching. Project owners can inspect metadata at `/api/projects/:id/files` but do not receive private file contents through this endpoint. Deletion rejects files referenced by records. File fields in records contain the file identifier, not a public URL.

No filesystem paths or remote download URLs are accepted. These checks are not malware scanning: untrusted documents should still be handled carefully by recipients. Larger-scale deployments should move content to private object storage with equivalent access checks and add malware scanning. Public asset hosting, image transformations, file sharing and antivirus scanning are not included.

## Validation

`node --env-file=.env --test tests/automation.integration.mjs` creates and destroys an isolated PostgreSQL database. It checks transactional enqueue rollback, duplicate events, concurrent workers, retry backoff, crash recovery, exhausted leases, notification isolation, file cross-member/cross-app isolation, malformed upload rejection, download headers and webhook address policies. HTTP tests use explicit fixture identities; full authentication/session coverage remains in the main backend integration suite.

`node --env-file=.env --test tests/database-recovery.integration.mjs` additionally uses the existing local Compose database container's matching `pg_dump` and `pg_restore` tools. It dumps a disposable source database, closes its connection pool, restores into another disposable database and verifies collection definitions/revisions, member roles, record data/versions, private file bytes and workflow jobs. The restored worker reclaims an expired lease and delivers one deduplicated notification. Both test databases are removed afterward. This verifies logical backup/restore and worker process-state independence; it does not simulate physical disk loss, PostgreSQL crash recovery or a full deployed-service restart. Scheduled backups, off-machine storage, encrypted backup retention and automated restore drills are still operator responsibilities.

No live external integration has been exercised: webhook HTTP delivery is tested through injected transport, with deterministic destination-policy and credential-binding tests. There are no built-in payment, email, CRM or calendar connectors; the generic webhook action is the integration boundary. Private file delivery and notifications run against real local PostgreSQL in the integration suite.

`node --env-file=.env --test tests/workflow-engine.integration.mjs` verifies conditions, ordered record updates, completion markers across later-step failure, per-step webhook keys, revoked ownership, invalid schema fields/types, cross-app recipients, one-shot scheduling, concurrent schedulers and interval cadence. It uses an isolated database and fake webhook transport.
